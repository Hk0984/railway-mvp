# Railway Lab

[公開版](https://hk0984.github.io/railway-mvp/)は、OuDia2ndのダイヤを使う1路線向けの乗換案内と混雑推計ツールです。ブラウザ内で動作し、はじめに架空の5駅・72列車で試せます。

## 0.7の使い方

1. **データ設定**でOuDia2ndを開き、対象ダイヤを選びます。種別の営業区分を確認し、混雑を算出する列車の輸送定員を1編成あたりの人数で入力します。
2. **乗換案内**で路線内の発着駅と出発・到着時刻を設定します。翌日0時30分は `24:30` と入力します。
3. **混雑ダイヤ図**を使う場合は、データ設定で1日あたりの駅別乗降人数を入力し、朝・日中・夕方・夜の割合を合計100%にします。路線外の需要を含める場合は方面ごとに流入・流出人数と接続駅を設定します。直通方式では対象ダイヤの列車を指定します。
4. 設定を保存し、**混雑ダイヤ図**の「混雑を計算」を押します。スジや区間を選ぶと推定人数・輸送定員・混雑率を確認できます。 分岐がある路線では「表示経路」で系統を切り替えます。「表示方向」と「スジ線の太さ」でダイヤ図の表示を調整できます。時刻の記載がない通過駅は前後の記録時刻を結び、途中の停車駅の時刻が欠ける区間は破線で表示します。

「需要の日区分」で平日（月〜木）・金曜日・土休日を選び、駅別人数と時間帯の配分をそれぞれ保存できます。金曜日と土休日の専用設定を保存するまでは、平日（月〜木）の設定を使います。「対象ダイヤ」は個別に選べるので、たとえば金曜日の需要を平日ダイヤで計算できます。乗車上限は全日区分で共通です。

目的地への到着時刻を指定する場合は、「時間帯の基準」で「目的地に着く時刻（上下別・1時間ごと）」を選びます。上り・下り別に、1時間ごとの割合をそれぞれ合計100%で入力します。指定枠に目的地へ到着する便へ配分し、便がない需要は未配分になります。「到着需要をなだらかに補間」をオンにすると、各1時間の合計を保ちながら、時刻の境目をひと続きの増加・減少でつなぐ曲線で配分します。

「駅の属性・利用目的」で主属性と任意の副属性を選び、通勤・通学・非定期の割合を設定できます。割合がすべて空欄の駅には属性の初期値を使います。副属性は初期値と行き先の傾向に25%反映します。住宅地、事業所、学校、商業地、歓楽街の傾向は架空路線用の仮定です。駅別人数は入力値を使います。「駅の属性・利用目的から到着時刻を推計」を選ぶと、利用目的と出発・到着駅の属性から時間帯も推計します。手動の時間設定を選ぶと、各時間帯の割合を保って行き先を配分します。

入力した駅別乗車人数を、到達可能な各駅の降車人数と行先重みで振り分けます。降車人数は行先の重みであり、推計した駅別降車人数との完全一致は保証しません。路線外方面の人数は登録順に割り当て、駅別集計に含まれる流入・流出は接続駅の入力から差し引きます。ODを作成できない人数と、時刻条件で列車に配分できない人数は「需要と計算条件」に表示します。

同じ列車に乗り続けて到着条件を満たせる場合、乗換での短縮が3分未満なら乗り続ける経路を優先します。目的地到着時刻を基準とする場合は、指定された到着枠の中で判定します。

混雑率は推計した車内人数を輸送定員で割った値です。「営業区分・輸送定員」の「乗車上限の混雑率（%）」に値を入れると、駅で降車した人数を差し引き、指定割合に達するまで次の利用者を乗せます。上限を超える分は目的地まで行ける後続便を待ちます。空欄では上限なしで計算します。上限を使う場合は営業列車の輸送定員を設定してください。停車中、輸送定員の未登録、配分対象外などはヘイズを省きます。路線外方面の設定は対象路線内の混雑推計に使います。乗換案内の検索範囲は路線内です。

設定はブラウザ内に保存できます。バックアップには「設定のJSONを保存」を使ってください。旧プロジェクトJSONにも対応し、駅利用者数と路線外方面の設定がない場合は保存済みの時間帯別ODを利用できます。

ローカル実行は `npm ci` → `npm run dev`、テストは `npm test` です。開発サーバー稼働中に `node tests/browser-renewal.mjs` を実行すると、Chromiumで3画面を検証できます。

## 起動

Node.js 20.19以上または22.12以上を使用します。確認環境はWindows / Node 24.22.1です。

```powershell
cd railway-mvp
npm.cmd ci
npm.cmd run dev
```

ブラウザで `http://127.0.0.1:5173` を開きます。PowerShellのスクリプト実行制限を避けるためWindowsでは `npm.cmd` と記載しています。他OSでは `npm` を利用できます。

```powershell
npm.cmd test
npm.cmd run build
```

本番用静的ファイルは `dist/` に生成されます。ローカル確認には `npx.cmd vite preview --configLoader runner --host 127.0.0.1` を使用できます。インストール後のアプリ実行にインターネット接続は不要です。`index.html` をファイルとして直接開く方法には対応しません。制限されたWindows環境でも設定ファイルを読み込めるよう、各npmスクリプトはViteのrunnerローダーを使用しています。

## 使い方と動作範囲

1. **ダッシュボード**：駅数、選択ダイヤの列車数、平均運転間隔、登録需要、時間帯別の列車始発本数、路線概略。
2. **ダイヤデータ管理**：対応する `.oud2`、プロジェクトJSON、駅CSV、OD明細CSVの読み込み。JSON・CSVの保存。複数ダイヤの切り替え、文字コード指定。失敗した読み込みで現在のデータは置換しません。
3. **ダイヤ分析**：発車駅・着駅・方向・種別・時間窓の指定、駅別／方向別の停車発車本数、時間帯別発車本数、運転間隔の平均・中央値・最大・母標準偏差、隣接駅間の最短所要時間、任意ODの直通列車・有効列車、期待待ち時間と利用可能割合。
4. **駅・沿線都市**：人口、雇用、学生数、商業・観光指標、鉄道利用率の編集。ID・駅名・所属・乗換情報は駅CSVまたはJSONで編集できます。
5. **OD需要推計**：通勤・通学・私事の目的と時間帯ラベル、発生係数、吸引係数、βの設定。手動所要時間行列、または選択ダイヤの最短直通乗車時間を使った重力モデル。発生量・配分量・未配分量を表示。
6. **OD行列・出力**：行列と発駅別合計、目的・時間帯・出典付き明細、行列CSV／明細CSV出力。
7. **経路検索**：日本語部分一致の駅候補、発着入替、出発／到着指定、前後の便、最大乗換0〜4回、最低乗換時間、直通のみ、対象種別、データセット・ダイヤ指定。複数候補を早着／遅発・乗換数・乗車時間で並べ、展開カードに乗降・途中駅・乗換待ちを表示。路線内の有効直通本数と乗換込みの有効出発機会を区別し、時間帯需要と比較します。
8. **時間帯別OD**：通勤・通学・買物・その他私事の目的別発生係数と時間分布、帰路率・滞在分布を編集。日間ODを1時間／15分に配分し、日間人数・個別時間枠の人数を編集できます。出典を保持し、時刻付き明細をCSV出力します。

11. **需要校正・シナリオ・比較**：実測CSVの用途・条件を確認してIPF／係数探索、検証、感度分析、保存シナリオ・同一需要のダイヤ比較。
12. **複数路線・統合配分**：ダイヤ日区分対応・徒歩連絡・駅到着分布・統合ODを設定し、複数路線共通の定員制約と旅客状態、OD流動・混雑要因を分析。

「ダイヤデータ管理」で2つの実ファイルを順に読み込むと、データセットライブラリに両方が残ります。「経路検索」で使うデータセットを選び、ダイヤを指定してください。選択データセット以外の便を混ぜず、同名駅でも別データセットの駅は別IDです。手動の徒歩連絡を設定した場合だけ、複数データセットを併用できます。原ファイルをアプリに自動同梱したり外部取得したりはしません。

変更はこのブラウザのlocalStorageに保存されます。大きいプロジェクトは標準のCompressionStreamでgzip圧縮して保存し、初期MVPの非圧縮保存データも読めます。保存中・容量超過は画面に表示します。CompressionStream対応の現行ブラウザを使用してください。ブラウザデータ削除で消えるため、JSONを保存してバックアップしてください。都市データ・手動行列の変更や駅CSV読み込み時は登録ODを消去します。係数を変更した後は生成ボタンで再計算します。OD生成・OD CSV読み込みは登録済みOD全体を置換します。JSONには係数・手動行列・OD・読み込みメタデータも含まれますが、画面フィルターは含まれません。

## 計算上の仮定

- 時刻は**運行日の00:00からの秒数**。JSONでは日付を跨ぐ時刻を86400以上で指定します。画面は24:10等と表示し、日付に丸めません。所要時間・移動負担は分、βは1/分、需要は人、鉄道利用率は0〜1です。
- 運行本数は停車駅の**発車本数**です。通過と着時刻しかない終着は除外します。運転間隔は指定窓 `[開始, 終了)` 内の発車時刻差で、2本未満は未算出です。
- `Canceled=1` は登録したまま運行分析・経路検索から除外します。回送・試運転等の旅客営業可否は名称から推定しません。「営業区分・定員」で営業／非営業／要確認を明示設定します。未設定は要確認として検索・新規の需要用ダイヤ費用・配分から除外。既存の固定費用・需要は自動変更しません。
- 有効列車：同時刻以降に出発し同時刻以前に到着する別列車が存在し、少なくとも一方が厳密に優れている列車を除外します。同一着発時刻の重複便は両方を有効とします。指定窓外の後続列車も比較に含みます。
- 期待待ち時間：指定窓内で一様に到着し、**最速到着する直通列車**を選びます。到着同時なら遅い発車を選びます。利用可能な旅客到着時刻に条件付けた平均であり、未充足時間は利用可能割合で別表示します。窓の終了後の出発便も候補にします。翌日のダイヤ繰り返しは仮定しません。
- OD費用のダイヤモードは、選択ダイヤ全体の**最短直通乗車時間**です。待ち時間・乗換・駅アクセス・時間帯分布は加算しません。欠損着発時刻・通過駅の乗降は使いません。
- 発生量 `O_i = population_i × railShare_i × generation`。全目的で人口を基礎にし、目的ごとの発生係数は利用者が設定します。吸引力 `A_j = employment_j × employmentWeight + students_j × studentWeight + attraction_j × attractionWeight`。両者は独立です。係数に実測校正の裏付けはありません。
- `T_ij = O_i × A_j exp(-βC_ij) / Σ_(k≠i) A_k exp(-βC_ik)`。対角は配分しません。欠損費用・吸引力0の目的地は対象外。候補がない場合は未配分として報告します。浮動小数点のアンダーフローを抑えるため対数重みを正規化します。
- 従来の「OD需要推計」の時間帯はラベルです。新しい「時間帯別OD」では、日間往路を目的別の分布で実際に分割し、固定移動時間と滞在分布から帰路を推計します。両モデルは独立して保持します。実測・手動値を自動的に推計値として扱いません。
- 人数は内部で丸めません。画面の小数丸めにより見かけの行和に差が出ることがあります。CSVは丸め前の値です。行列表示は全目的・時間帯・出典の合算です。

## OuDia2ndへの対応

**部分対応です。完全互換ではありません。** 詳細は [FORMAT.md](docs/FORMAT.md) を参照してください。

- FileType **1.07 / 1.17** の階層・駅・種別・複数Dia・方向・駅時刻・番線を抽出。他の版は互換と決めつけず拒否します。
- UTF-8優先、失敗時Shift_JISの厳密デコードによる自動選択と、文字コードの明示選択に対応。
- `BrunchCoreEkiIndex` に基づき分岐の派生行を基幹駅IDに統合。同名だけでは統合しません。原時刻表行IDと原EkiJikokuも保持し、連続する同一駅の別行着発を同一訪問として分析します。
- `OuterTerminal` と駅作業コード4の路線外始発・終着を境界駅別に保持し、管理画面と直通列車一覧に表示します。外部駅をOD用の都市として自動追加せず、外部区間時刻は内部所要時間に混ぜません。
- 解析運行日の起点を選択できます。既定はファイルの `KitenJikoku` に合わせ、設定がなければ00:00。起点未満の明示時刻を+24時間で表現する**解析規約**であり、欠損時刻の推定ではありません。両実ファイルは04:00起点で検証。

計算関数はDOM・localStorageから独立し、駅IDを参照します。Timetableを配列として保持し、需要には目的・時間帯・出典があります。経路検索・時間帯需要・需給比較もそれぞれ独立モジュールです。配分をWeb Workerで実行し、0.5では疎ODリストと直通の発駅プロフィール共有を使います。乗換多数の路線走査・大規模描画とメモリ削減は今後の課題です。

0.2ではデータセットIDと駅IDの組で検索対象を識別します。旅程は列車ID・ダイヤID・乗降駅・明示着発・乗換関係を構造化して返します。TransferLinkは方向・徒歩秒数・設定根拠を持ち、UIで追加・削除できます。プロジェクトJSONに日間・時間帯需要を、**全データセットJSON**にライブラリ・徒歩連絡・各プロジェクトを保存できます。どちらも既存のJSON読込ボタンから読み込みます。ライブラリは圧縮してブラウザ内にも保存します。

検索は登録された運行日内に限ります。翌日の便の自動繰り返し、路線外区間、別レコードを確定直通とする処理、運賃は未実装です。徒歩リンクは列車間の乗換に使い、徒歩を含む容量配分に対応しました。徒歩だけのOD移動は扱いません。積分セル内の中点近似、旧方式の登録順・新方式の端数タイブレーク、大量結果の転送・描画コストが残ります。

検証手順と結果は [VALIDATION.md](docs/VALIDATION.md)、次の実装優先順位は [ROADMAP.md](docs/ROADMAP.md) を参照してください。
