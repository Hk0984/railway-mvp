# MVP 0.6：同時刻競合・時刻仮定・診断

現行仕様は [MVP_0_6.md](MVP_0_6.md)。統合画面で同時刻一括方式を選ぶと、降車・需要・徒歩完了を反映した後、FIFOの同着集団から全便へ提案し、共通残定員に比例配分して同時に反映する。残りは同時刻候補・後続経路へ再評価する。整数の同余はOD内容等で決め、入力順を優先しない。同一車両に同時刻の複数停車があっても定員を共有する。

時刻は枠中点・枠開始・一様積分・指定分布積分を選べる。C/Dの整数は累積確率丸めで細かい枠の先頭集中を防ぐ。締切は明示秒だけ加算し、発着時刻の秒を推測しない。従来設定未指定は0.5互換。

新方式の定員制約結果には、需要発生前・待機・車内・徒歩・完了・経路なしの台帳を追加。途中の状態変更と最後に収支を検証する。全件記録は分割元・経路・乗降・再探索・未輸送理由を追跡できる。概要記録と区別し、50万ログ超は明示エラー。時系列イベントは別に需要を発生させず、乗換の延べ乗降と実人数を分ける。

固定需要比較は行順を正規化し、条件差・完了率・除外人数を表示する。シナリオ幅は統計的信頼区間ではない。単一結果内の停車オブジェクトは共有し、索引原本とは分離する。以下は過去版の記録。

# MVP 0.3：営業区分・旅客配分・区間人数

## 営業区分と保存互換性

`serviceClasses.types` に種別ID別の営業／非営業／要確認と設定根拠、`serviceClasses.trains` に `[ダイヤID,列車ID]` をJSON化したキーの個別上書きを保存します。名称変更で分類は変わりません。未設定は要確認、運休も旅客利用不可です。旧schemaVersion 1のJSONは読み込めますが、分類は利用者が設定してください。既存需要・固定費用は自動変更しません。

参照ファイル用の初期分類はSHA-256・FileType 1.17・種別数の一致時のみ表示し、利用者の明示適用が必要です。名称辞書による自動承認ではありません。営業実態を保証するものではないため設定根拠と各便を確認してください。琴町線の臨時種別は要確認（現ファイルに該当便なし）です。

既存の全列車分析は保持し、営業・非営業・要確認を別表示します。旅客検索・新しい需要用ダイヤ費用・配分は営業のみです。解析用 `passengerOnly:false` 索引では配分を拒否します。

## 配分モデル

`assignment.ts` はDOM・保存処理から独立しています。入力は出典・往復・目的・時間窓を持つ時間帯ODです。同じ需要を異なるダイヤに配分できます。

- 時刻は運行日00:00からの秒、人数は人、一般化負担は分。24時以降も同じ軸。翌日の便を自動追加しません。
- OD枠内で駅へ一様到着すると仮定。発車時刻、最大初期待ち、最大総所要時間の成立境界で枠を分割し、セル中点を到着時刻として保持します。成立性と相対費用が一定になる区間ごとに配分します。
- 最短方式は駅到着から目的地到着までを最小化。同着時は乗換回数、一般化負担で選びます。初期待ち上限・最低乗換時間・総所要上限を満たす経路のみ使用します。
- ロジット方式の負担は `乗車分×係数 + (初期待ち分+乗換待ち分)×係数 + 徒歩分×係数 + 乗換回数×ペナルティ分`。目的別非負係数・感度を編集可能。負担順で最大K候補に絞り `exp(-感度×負担差)` を正規化します。乱数ではなく期待人数です。
- 候補は最初の便ごとに時間・乗車・徒歩・待ちのトレードオフを保持した非劣旅程です。全経路の網羅ではありません。経路相関・類似度の補正は未実装です。
- 実数配分は残差補正、整数配分は最大剰余法。整数方式には整数ODと整合する時間窓が必要で、窓の切断で分数になる場合は拒否します。対象窓外は別記し、対象需要＝配分済み＋未配分を検証。OD行・到着セルごとの人数も照合します。
- 経路なし・未確認便のみ・探索量上限などは理由付き未配分として保持します。不完全な結果を配分成功にしません。

## 列車・区間集計

旅程の各乗車区間で乗車位置に加算・降車位置に減算し、その間だけ断面人数へ計上します。分岐駅の原行対応を保った実列車の訪問順を使用し、通過・運転停車等では乗降しません。

乗換旅客はODでは1人、2列車利用なら乗車イベントは2回です。延べ乗車、列車別利用人数、最大車内人数を区別します。検証では元旅程から再集計し、乗降・断面人数・定員・混雑率と照合。終着後は0です。

定員は `Train.capacity` を優先し、なければ `typeCapacities`。不明は推測せず人数だけを表示し、既知は人数÷定員です。100%超も全員乗車とする非容量制約モデルで、積み残し・次便繰越・混雑による再選択は未対応です。

## UI・保存・CSV

営業区分設定→時間帯ODの生成・編集→旅客配分の順で利用します。方向は計算後の表示フィルターで、乗換を消しません。実測ODが入力でも列車人数は推計です。2方式比較は同じ索引・需要を使用。Workerで実行・中止可能。設定はJSONとブラウザに保存、結果はメモリ内のみで再起動後は再計算します。条件変更で古い結果を無効化します。

列車集計・区間乗降・配分旅程・未配分の4CSVに対応。混雑率は倍率（1＝100%）、時刻は秒です。旅程CSVは1乗車区間1行で、全行の人数合計は乗車イベント数になります。

配分UIは1データセット・1ダイヤ。共通エンジンはStationRefと明示TransferLinkを使いますが複数データセット配分UIは未対応。路線外OD・未確定のレコード間直通・増解結を推測しません。既存警告を表示・結果診断に保持します。

## 高速化・計測

旅程配列・文字列コピーを親経路共有へ変更、乗車候補を数値IDで索引化し駅参照を再利用。同じProject・ダイヤ・分類・徒歩条件なら索引を再利用し、1プロジェクトにつき3条件までキャッシュします。外部コードで駅時刻を直接変更した場合は `invalidateRoutingCache` を呼んでください。

`tests/performance.test.ts` は保存した0.2実装と全列車・同条件で旅程全体・候補数の一致を検証。`artifacts/performance-comparison.json` に前後の索引・検索時間とheapUsed差を記録します。測定例：琴町線早着384→147ms、乗車時間順12.3→6.7秒。端末・GC・並行負荷で変動します。heapUsed差はGCを含む観察値でピークメモリではなく、精密な削減率は主張しません。配分用の候補保持は通常検索より重く、多数OD・多乗換では長時間になり得ます。探索量上限は維持します。
