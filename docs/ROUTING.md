# 時刻表に基づく経路検索

## 構造とアルゴリズム

`routing-model.ts` は StationRef / TransferLink / DatasetSelection / RouteQuery / Journey を定義します。StationRefはデータセットIDと元の駅IDの組です。別データセットの同名駅や同じローカルIDは接続しません。分岐の元行IDと物理駅IDの対応は既存パーサーのメタデータに保持し、統合後の訪問にはsourcePositionIdsも付けます。

`buildRoutingIndex` は指定した各データセットの**一つのダイヤ**の実レコードだけを索引化します。取消便・対象外種別を除外し、着時刻が明示された降車と、発時刻が明示された乗車を結びます。扱い2の通過・運転停車は乗降不可。明示したpickupAllowed / dropoffAllowed=falseも尊重します。

`journeyProfile` は乗車回数をラウンドとする多ラベル時刻表探索です。1ラウンドで一つの実列車レコード内の乗車駅→後方の降車駅を展開します。到着時刻・最初の発時刻・徒歩時間、乗車時間優先時は乗車時間も比較してラベルを刈り込みます。同じ便の同じ乗車位置への到達をまとめ、以前の少ない乗換ラウンドとの支配関係も利用します。乗車時間優先時には直前の車両レコードを区別して、再乗車制約による誤った刈り込みを避けます。

RAPTORの「乗換回数ごとのラウンド」という考え方を参照していますが、路線をラウンドあたり一回走査する最適化版RAPTORを実装したものではありません。[原論文の紹介](https://www.microsoft.com/en-us/research/publication/round-based-public-transit-routing/)との違いを明確にし、実装名はラウンド型の時刻表多ラベル探索とします。

出発指定は最初の発車が指定時刻以降、到着指定は最終到着が期限以内となる候補を検索します。到着指定の時刻優先では最も遅く出発できる候補を先に表示します。乗換数・乗車時間優先も、それぞれ第一基準として並べ替えます。同じ実列車レコードのまま途中駅で乗降するものを別の乗換として水増ししません。別レコードは勝手に直通結合しません。

乗換は `次便発 ≥ 前便着 + 徒歩秒数 + 最低乗換秒数` を満たすものだけです。徒歩リンクのない同一StationRef内の乗換は可能ですが、異なるStationRef間の移動には明示TransferLinkが必要です。方向に従った最短の明示徒歩連絡列を用います。最初の乗車まで・最後の降車後の徒歩だけの移動は今回対象外です。

列車間の乗換では、乗換待ちは「次便発−前便着−徒歩」と定義し、最低乗換時間も含みます。乗車時間・徒歩時間・乗換待ちの合計が旅程全体の所要時間と一致します。検索指定時刻から最初の便までの初期待ちは総所要時間に含めず、サービス評価の期待待ち時間と区別します。

## APIと整合性

```ts
const index = buildRoutingIndex(
  [{ datasetId, project, timetableId, allowedTypeIds }],
  transferLinks,
);
const result = searchJourneys(index, query);
const errors = validateJourney(index, query, result.journeys[0]);
```

Journeyには、各区間のdatasetId / timetableId / trainId / trainNumber / typeId、乗降駅と時刻、元訪問の添え字、途中停車・通過、乗換のfrom/to・徒歩連絡ID・待ち時間を保持します。列車別配分で乗車・降車・区間を特定するための基盤です。本格的な配分・混雑はまだ計算しません。

`validateJourney` は区間を選択ダイヤの列車へ再照合し、乗降可否・途中駅情報・最低乗換時間・明示徒歩・集計時間を検査します。UIは表示前にこの検査を通します。

既知の実ファイルでは各ダイヤを混ぜず、上下方向・途中始終着・分岐・深夜・路線外表示を確認しています。原ファイルの未知項目や境界不一致の警告は、画面上部と検索対象の警告欄に保持します。路線外駅を索引へ加えたり、外部区間の時刻を経路に加えたりしません。

## 有効サービスの定義

直通有効列車は従来どおり、別便が同時刻以降に発車し同時刻以前に到着し、どちらかが厳密に優れる場合に除外します。同一着発の等価な別便は直通本数では別に数えます。

乗換を含む有効サービスは**最初の発車時刻ごと**に最速到着の旅程を一つ代表とし、厳密に後発の出発機会で同時刻以前に着ける機会を除きます。組み合わせ違いの旅程を別本数として数えません。画面では「有効出発機会」と表示し、直通本数と分けます。

集計窓は `[開始, 終了)` です。窓終了後に発車する後続便も検索した上で有効判定を行います。有効発車時刻・間隔の平均、中央値、最大、母標準偏差を返します。2機会未満では間隔は未算出です。

期待待ちは到着時間窓上で積分し、最速到着便を選ぶ一様到着を仮定します。便に乗れる時間に条件付けた平均と、利用可能な時間割合を両方示します。終便後の利用不可時間を無限待ちや0分待ちに置き換えません。

## UI・保存と制限

検索画面は日本語の部分一致候補と、データセット・駅IDを含む選択肢を用います。同じ名称のデータセットもD番号で区別し、計算には永続的なデータセットIDを使います。新規.oud2のIDはローカルSHA-256、旧JSONは初回のUUID、架空サンプルは固定IDです。

入力・選択条件の変更時には再検索します。前の便は現在の先頭候補より早い到着期限、次の便は先頭候補の発車より1秒後を条件に検索します。候補がない場合は検索時刻を1時間動かします。候補表示は6件までで、表示上限と計算上の上限を区別します。

計算は登録された運行日の有限ダイヤに限ります。翌日の反復、外部区間、確定できないレコード間直通、運賃、距離、混雑、番線の推測表示は行いません。0.3では種別・便の明示的な営業区分を共通適用し、非営業・要確認を旅客検索から除外します。欠損着時刻では降車・乗換を生成しません。

最大乗換は0〜4回、探索の展開量上限は1,200万です。超過した場合は絞り込みを求めるエラーとし、不完全な候補を成功として返しません。0.3で親経路共有・索引キャッシュ・配分Workerを追加。通常検索のWorker化・完全なrRAPTOR相当の高速化は今後の課題です。性能比較は [配分仕様](ASSIGNMENT.md) を参照してください。

今回のローカル検証では、琴町線の時刻優先検索は数百ms、バスは数ms〜数十ms程度でした。乗車時間優先は保持する候補が多く、琴町線の乗換検索で数秒かかる場合があります。ブラウザのメインスレッドで計算しているため、この間操作が止まる可能性があります。性能値は環境と条件によります。
